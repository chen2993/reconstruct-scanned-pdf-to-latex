# 多 Subagent 并行协作

几百页教材靠单执行者串行转写会拖很久，而并行又会带来重复接口、样式漂移和互相覆盖。本文件规定分工方式、任务包内容、并发节奏与验收门，让并行真正提速而不是制造返工。

## 0. 先做能力预检

并行不是随时可用，开始前必须先确认运行环境真的具备两项能力，否则越往后代价越大：

1. **原生多模态读取**：打开一张已拆出的页图，确认能看清内容。若返回“模型不支持视觉”之类的占位文本，说明当前会话读不了页面——此时任何转写都无法进行，必须立即停下来告知用户并请其切换模型，禁止改用 OCR 或 PDF 文本层替代。
2. **任务分派**：确认运行环境确实能派发子任务（工具存在且调用成功）。不支持时按单执行者串行推进，不要停在“已派发”的空状态上，也不要把任务包写出来了却没人执行当成已完成。

预检结论写进 `progress.md`：用的是哪个模型、是否支持视觉、是否能分派。后续单元遇到能力缺失时直接看这条记录，不必重新试错。

## 1. 角色与边界

**主执行者（调度者）** 独占以下职责，执行单元一律不碰：

- 冻结并发布基线：`.cls`、`docs/class-api.md`、样式卡片、`semantic-audit.json`；
- 切批、生成任务包、派发、验收、更新进度与复核记录；
- 更新 `.cls` 与公共接口，处理样式缺口；
- 操作 Git：提交检查点、创建标签。

**执行单元** 只负责被分配页面内的转写与自检：

- 只写任务包白名单里的 `latex/pages/pages-xxx.tex`；
- 只读本页独立 PNG（含相邻页用于判断跨页承接），不读其它单元的文件；
- 遇到未登记样式、样式变体或无法表达的版式，立即停工并写 `reviews/style-gaps.md`，不做就地近似；
- 不碰 `.cls`、`main.tex`、审计配置、样式卡片与 Git。

## 2. 任务包必须自带上下文

执行单元不能靠猜，也不能回头翻对话。每个任务包必须包含：

1. 本批连续页面范围与源页标识，以及允许修改的文件白名单；
2. 当前样式摘要版本号；
3. 该批实际会用到的样式卡片（不附无关卡片）；
4. 该批页面分型（章节首页、普通正文、图表/公式页、封底等）；
5. 停工反馈格式；
6. 跨页交接信息（仅当批次边界落在开放的可跨页所有者内）：环境名、起始页面标识、样式卡片版本、嵌套层级。

`scripts/orchestrate.py next` 会生成这份任务包到 `.reconstruct-scanned-pdf-to-latex/dispatch/<batch-id>.md`，内容来自 `dispatch.json`、样式卡片、`page-types.json` 与跨页边界扫描。主执行者可以在包内追加本批特有说明（例如“`pages-011/012` 已提交，本批实际从 `pages-013` 起”），但不要删减上述六项。

## 3. 图片读取纪律

并行会成倍放大上下文消耗，图片是主要成本，因此每个单元都要遵守同一条纪律：

- 用 `scripts/crop_page.py` 先出总览（`--overview`，不占预算）定位，再只截需要精读的区域；**宽度决定清晰度**，横带只切高度不提高清晰度；
- 左右留 0.03/0.96：正文常排到版心边沿，x 范围收到 0.09 会切掉行首字；
- 一页通常 1–3 块就够；不要为了“看全”把整页均分成十几条；
- 一轮只看 1–2 张图，读完再读下一张；需要扫多页时先用结构化信号（页数、`MediaBox`、墨迹密度、日志警告）缩小范围；
- 不靠放大补清晰度（`--scale > 1` 只是插值）；页图源分辨率不足时回到拆页阶段用更高 DPI 重出。

### 读图预算是硬上限，由脚本强制

每页默认 **6 次**读图（`--overview` 总览不计入），**裁剪即计数**——`scripts/crop_page.py` 会在产出裁图后自动登记，额度用尽时直接拒绝裁剪并提示停下报告。这不是纪律口号：实测有单元为了“更仔细”把一页裁成 20 多张逐张读，上下文烧光、任务中途崩溃，前面读的全白费。

- 超预算 = **任务失败**，不是“更仔细”。对应单元应停下并用 `BLOCKED` 报告卡在哪一块。
- 确实需要更多额度时，由**调度者**显式提高上限（`--reset-budget N`）并在进度记录里说明原因，不由单元自行放宽。
- 查余额与整批状态：`python -X utf8 scripts/read_budget.py <project> check pages-013`、`... report`。

### 防止图文错配

并行读图与共用文件名会造成**图文错配**：拿到的可能是别页的图，从而得出完全错误的结论（实测有单元因此误判“全书页码偏移了 6 页”）。

- 裁图文件名**必须带页号前缀**（`tmp/crops/p013_b1.png`）；多个单元共用 `tmp/`，无前缀的公共名会被并发单元覆盖——实测两张本应不同的裁图逐字节相同，单元看到的是别页的页眉；
- **不要在同一条消息里并行读多张图**，一次 1–2 张；
- 拿到图先核对**可自证的锚点**（页眉、印刷页码、章节标题）与本页标识是否一致；
- 不一致时先怀疑错配：单张重读 + 换新文件名重裁，**不要**先宣布“原书页码偏移”或去改编号。重裁后仍不一致，才按“原件与预期不符”报告，并附重裁文件名与看到的页眉文字。

### 视觉能力自检

单元开工前先裁一张图**亲自读**，确认这条路径有视觉能力。若返回“不支持视觉”之类的占位文本，立刻停下报告——**不要派下二级代理代读**：实测下级可能被固定在无视觉路径上，同样读不到图；图片必须由单元亲自裁、亲自读。

用户说“不要一次看这么多照片”“避免过大图片”“降低上下文长度”时，立刻把批量降下来，不要找理由继续铺开。

## 3.5 车道：规模上来之后的并行形态

批次解决"一次推进多少页"；数百页规模需要**车道（lane）**：把全书切成几条互不重叠的连续区段，各自独立派发与验收。实测项目在 527 页规模上同时跑十几条车道。

- **车道**是页面的划分，区段互不重叠、边界固定（通常按章或大节切，避免把一道题切成两条车道）；
- **批次**是车道内部再切的推进单元，仍按"转写 → 复核 → 编译 → 验收 → checkpoint"逐批推进；
- 每条车道有自己的边界上下文：起止页、该区段的章节结构、以及"进入时是否已在某个跨页所有者内部"。

调度者必须为每条车道准备三样东西，否则单元会各自猜：

1. **共用作业须知**（各车道共用）：角色、只写白名单、读图方法与预算、环境映射表、跨页承接规则、汇报格式；
2. **本车道作业须知**：页号区间、本区段特有的坑（行首字位置、特殊版式）、已提交到哪一批；
3. **全书结构地图**：各章/各习题集/综合题的起始页与对应结构命令。单元靠它核对"我这页是不是某一节的第一页"，避免把结构命令写错位置或重复。

结构地图是**派发前**从目录页读取得到的派发材料，不写进页面源码。单元仍按自己读到的原书内容决定 `\begin`/`\end`，但**结构命令的落点**要与地图一致；不一致时报告，不自行裁决。

车道不改变单元纪律：每个单元仍只写白名单内的文件、仍受读图预算约束、仍按"读完一页就写一页"的节奏推进，任何时刻被打断都不丢已完成的页。

## 4. 并发节奏

并发上限由运行环境实际支持的能力决定，然后用调度器固定下来：

```powershell
python -X utf8 scripts/orchestrate.py <project> plan --batch 10 --concurrency <N>
python -X utf8 scripts/orchestrate.py <project> next      # 生成任务包并派发
python -X utf8 scripts/orchestrate.py <project> verify b001-010
python -X utf8 scripts/orchestrate.py <project> checkpoint b001-010
```

- `--concurrency N` 表示最多 N 个批次同时在飞；达到上限后 `next` 排队而不是继续派发；
- 每个批次内部仍是三轮：原生多模态转写 → 逐行内容复核 → 编译与版式复核；
- 批次完成后主执行者验收，通过才派下一批；`checkpoint` 会把该批提交为 Git 检查点；
- **“已派发”不等于“已完成”**：产物存在性和内容质量分开核对，只查存在会漏掉空文件与占位内容。

## 4.5 规范形态：一个调度者 + 多个执行单元

本技能的目标形态是**单个调度者管一批执行单元**，不是多个调度者并行推同一本书。用户在不同阶段各开一个会话是正常做法，不是并行抢队列——但这两件事的边界要分清。

### 会话与阶段：阶段是跨会话的

一本几百页的书往往跨越很多个会话，**一个阶段一个会话**（甚至一个阶段要分几次续跑）。因此：

- **状态必须落在文件里，不能留在对话里**。会话结束、上下文压缩、换模型之后再续跑时，唯一能依赖的是 `progress.md`、`reviews/`、`dispatch.json`、`style-cards.md` 这些落盘记录；
- **每个会话开工先读状态文件**，不要靠"上次说过什么"重建上下文；
- **阶段交接要留证据**：前一阶段留下的是产物与结论（纸型确认、样式卡片定稿、基线冻结），不是"我记得已经确认过了"；
- 续跑一个阶段时，先核对**该阶段的进入条件**（见 SKILL.md 阶段总表）是否真的满足，而不是假定上一会话已经做完。

### 边界条件：两个调度者同时推进同一本书会撞车

如果确实出现两个调度者**同时**写同一个项目（例如两个人各推一个页区间），调度器会撞车，原因是它按全项目状态设计：

- **`next` 取全项目最小的待处理批次**：两个调度者都调，就会互相抢批次，或各自以为对方会做；
- **`concurrency` 是项目级的值**，不区分调度者，两边各按上限派发会让实际并发翻倍；
- **`dispatch.json` 是单一文件**，同时写会互相覆盖。

所以：**同一项目同一时间只由一个调度者写入**。需要加速时用该调度者提高 `--concurrency`，而不是另开一个调度者共用队列。若要按页区间分工，就硬切区间并让各方维护自己的队列文件——但这是例外，不是默认形态。

### 跨页交接不要盲信自动扫描

接手一个区间的第一条边界时，不能靠"上一页文件"推断，因为相邻页当时可能还是**占位骨架**。`open_owners_at_boundaries` 扫描的是源码，因此它可能给出**幽灵交接数据**。

实测记录：任务包里的"跨页交接"清单被单元判定为不可信，单元改为**以自己裁图读到的原书内容为准**。这一点必须写进任务包，否则单元会照着错数据写 `\begin`/`\end`。

## 4.6 执行单元的粒度

`workflow` 类工具的单次运行实测并发约 14–16 个单元、总量上限约 1000。在这个量级下：

- **单页粒度**（每单元 1 页）可行，配套给上一页/下一页用于判断跨页，但只写 1 页；代价是调度次数多——数百页意味着数百次派发；
- **批次粒度**（每单元连续若干页）能显著减少派发次数，适合各页独立、跨页对象少的情况；跨页对象密集时再退回单页粒度；
- **失败集中在中途**：多个单元跑到一半失败，根因是**读图过多导致上下文耗尽**（有单元一页裁 20 多张图）。所以读图预算必须由脚本强制，不能只靠提示词提醒。

无论哪种粒度，单元纪律相同：只写白名单内的文件、受读图预算约束、按"读完一页就写一页"推进，任何时刻被打断都不丢已完成的页。

## 5. 收敛门

- 基线未确认前只允许做输入审计、拆页、方向修正、样式卡片与样式实现，不得开始批量转写；
- 出现新样式缺口时暂停该批，由主执行者补齐 `.cls`、API、卡片与审计配置，再通知所有受影响单元重新读取新版本；
- 每次验收前跑该批静态审计；跨页环境还要有真实编译验证，静态审计查不出静默作用域泄漏；
- 主执行者在合入时统一检查接口一致性与全局环境栈，不能假设各单元自行保持了一致。

## 6. 交接与恢复

长任务会跨会话、跨压缩继续，因此状态必须落在文件里：

- `progress.md`：当前目标、已完成阶段、关键量测（页数、纸张、章节锚点）、待办、已知阻塞，以及能力预检结论；
- `reviews/`：样式复核、样式缺口、图形复核、全书复核、最终复核；
- `dispatch.json`：每批状态与检查点哈希；
- `reviews/style-gaps.md`：未关闭的样式缺口，它阻塞相关批次的恢复。

后续单元靠这些文件恢复上下文，不依赖对话记忆。交接摘要按“任务 → 决策 → 证据 → 结论”写，保留可追溯的量测值而不是印象式描述。
